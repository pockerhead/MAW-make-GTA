# PLAN V2 — TASK-011: wanted level core

## 1. Review notes

- **Disconfirmation tested first.** A shot near a living bystander can create both `Shooting` and `Kill`; a call about its attack followed by a call about the corpse must not add either incident twice. In the proposed `Crimes::report`, `reported: bool` would prevent that duplication, so this counterexample did **not** falsify the proposed accounting. It is not covered by the plan's integration tests, however. The present checkout has only `WantedLevel { stars }` ([`wanted/mod.rs`](../../../../crates/gta_sim/src/wanted/mod.rs)), so runtime behavior cannot yet be tested. Add an attack-then-body gate with both calls observed.
- **Confirmed false attribution.** The plan's `Cause::Body(v)` resolves *all* incidents with `victim == v`. Current corpse perception knows only the corpse's `Entity` (`perception/mod.rs:263-270`); `DamageDealt` separately knows `shooter` and `target` (`combat/hitscan.rs:77-87`). Worked case: the player punches civilian V privately (+5 incident, unreported); a gang member later kills V; a civilian sees V's corpse and completes a call. The proposed resolver reports the player's old punch despite no witness to that attack. Restrict `Body(v)` to a player-caused `Kill` of V. Calls about `Attack(id)` may report the matching shooting/injury/kill because the existing hearing/Fight stimulus actually carries that attack.
- **A lethal shot changes the nearby-person predicate after the fact.** `fire_weapons` emits `ShotFired` before applying damage, then `DamageDealt` (`combat/hitscan.rs:221-263`). The proposed downstream `record_crimes` reads `Health.current > 0` after damage. If the only person within 15 m was killed by this shot, it records no `Shooting`, while an identical nonlethal shot records 10 heat. GDD §6.4 says a shot near people, without a surviving-person condition. Determine proximity at the shot, including the person killed by that same attack; exclude bodies already dead before it. Gate lethal and nonlethal versions of the same geometry.
- **Unbounded incident work is omitted.** A `Shooting` episode appends every attack to `Vec<u32>` and an incident's `last` is refreshed on every shot. Sustained fire with gaps below 5 s can keep one vector and the incident indefinitely. A simple bound is to retain attack IDs only for the maximum call/report lifetime and prune old IDs while preserving a reported incident's one-time accounting; document and gate the bound. Do not add an async task for the small current NPC population.
- **The Wasted message rule is too optimistic.** `NpcSystems` keeps running through `Wasted` (`flow/mod.rs:51-54`), while `WantedSystems` would be `Playing` only. Bevy 0.19.1 `Messages<T>` retains two update buffers and `MessageReader` owns its cursor (`bevy_ecs-0.19.1/src/message/messages.rs:193-228`, `message_reader.rs:34-44`). Clear `Messages<PoliceCall>` on exit from `Wasted`, as `flow/wasted.rs:156-160` already does for queued damage. Clearing incidents on entry is still needed. This makes the boundary explicit and prevents future incident-ID or report-source changes from reviving a stale call.
- **The plan's exact search gate is too brittle at the frame boundary.** `Time<Fixed>` defaults to 15,625 µs = 64 Hz (`bevy_time-0.19.1/src/fixed.rs:76,230-235`), and 10 s is 640 fixed ticks. But teleporting a physics character with `place_player` then running physics can change its position/velocity (`tests/common/mod.rs:102-111` sets Position and Transform only). Hold the player at a stable position or assert the measured `Position` each step; drive the threshold from `Time<Fixed>` and compare elapsed duration with a one-tick tolerance only if the actual fixed-tick order warrants it. A pure `search_step` boundary test should still be exact.
- **Two tests do not establish their stated property.** The proposed one-body test checks only Kill→Body and never the attack/body overlap. The proposed `stars_follow_a_heat_mutation` is a liveness test for star recomputation, not BRP reachability. BRP visibility requires `Reflect` registration and a runtime query/mutation through `tools/qa/brp.py`. Label these claims separately.
- **Resolved questions are reopened in the plan.** `TASK_FINAL.md` already resolves sub-threshold decay, `shooting_merge_seconds = 5`, `incident_memory_seconds = 60`, and repeat-call behavior. Section 5 of the original plan must not ask the owner again. Treat those values as data knobs and the answers as decisions.
- **Research verification.** The chosen buffered `Message` design matches [Bevy's 0.19.1 message API](https://docs.rs/bevy_ecs/0.19.1/bevy_ecs/message/trait.Message.html); explicit writer/reader ordering is required by [the buffer documentation](https://docs.rs/bevy_ecs/0.19.1/bevy_ecs/message/struct.Messages.html). `Time<Fixed>` supplies fixed elapsed/delta time as proposed ([0.19.1 API](https://docs.rs/bevy_time/0.19.1/bevy_time/struct.Time.html)). Avian 0.7.0 supports `SpatialQuery::cast_ray` with a layer filter ([API](https://docs.rs/avian3d/0.7.0/avian3d/spatial_query/struct.SpatialQuery.html), [filter](https://docs.rs/avian3d/0.7.0/avian3d/spatial_query/struct.SpatialQueryFilter.html)). RON 0.12.2 documents that fixed arrays use tuple syntax ([RON documentation](https://docs.rs/ron/0.12.2/ron/)). No newer library or added dependency is needed. Genre wiki descriptions in the original plan are only visual references; GDD §6.4 remains the rule.

## 3. Revised approach

Keep a headless wanted plugin that consumes **buffered messages**, records player crimes with attack/body identity, and awards heat once per *distinct reportable incident*. A corpse report proves only that the player killed that body; it does not prove older, unseen nonlethal crimes. A completed civilian call carries the cause captured when the call began. A cop fixture can report an incident immediately when it has LOS within the GDD 50 m witness distance. Search and decay run in `FixedUpdate`; HUD reads reflected wanted state in `Update` and uses `Time<Real>` only for blinking.

`WantedLevel` holds heat, computed stars, last known position, current seen flag, and continuous hidden-outside time. If heat is below 40, use the one-star circle/time rule per the resolved question. A new report updates heat, circle center, and timer once, regardless of repeated calls. Keep `Crime`, `Incident`, and `Crimes` private except the minimum read API needed by tests/T11; avoid exporting `classify`, `IncidentId`, `Victim`, `cop_sees`, and `in_view` as future public interfaces without an actual consumer. T11 can add its own police rules against a narrow wanted API when it lands.

## 5. Risk areas

- **Attribution is silent gameplay corruption.** Attack ID, victim ID, and shooter identity must remain separate. Body sight proves a death, not past punches/wounds; test the private-punch/gang-kill counterexample.
- **Temporal classification.** The health value observed downstream is post-shot. Fix the at-shot proximity rule before relying on near-person heat, and prove it for lethal, nonlethal, and already-dead targets.
- **Message lifetime and state re-entry.** Civilian calls can progress during Wasted. Explicitly clear queued calls and incidents at the correct boundary, and gate a call that completes around respawn.
- **Event order.** A missing `.chain()` among record, call, search, forget can make heat land a tick late or expire early. Assert the tick of award where deterministic.
- **Long firefights.** A merged shooting incident must not retain an unbounded attack vector; a bounded retention check is more useful than an arbitrary frame-time max.
- **Visual quality.** Star color, blink feel, and overlap with ammo are owner-run judgments. Keep automated claims to state and node behavior, and record screenshots for inspection.
