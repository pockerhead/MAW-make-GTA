# PLAN_V2 — TASK-008, T7 melee

## 1. Review notes

- **Disconfirmation tested first.** Counterexample: if `fire_weapons` consumed LMB only with a gun equipped, the proposed shared `ActionIntent.fire_requested` path would be wrong. It does **not** hold: `crates/gta_sim/src/combat/hitscan.rs:152-155` takes the flag before checking `loadout.held`; `src/input/mod.rs:191-199` raises it for an armed mouse press. Therefore `swing_melee` must run after `tick_loadouts` and before `fire_weapons` and take the flag only while unarmed. This order is a correctness condition, not merely an optimization.
- **The plan's claim that `DamageDealt.damage` is “exactly what `Health::take` gets” is true, but its stronger “damage shown == damage applied” wording is false for armour.** `character/health.rs:103-107` passes the amount to `apply_damage`, which absorbs armour first. The existing gun message reports the incoming amount. Keep melee consistent with that contract; assert a health drop equals message damage only on an unarmoured dummy. Add one armoured-target check for armour-first behaviour instead of changing the existing message semantics.
- **The proposed attack state machine has an ambiguous boundary and its tick table depends on one exact branch order.** In PLAN.md:208-214 the end-of-swing path resets `combo_left`, then falls through to the “no swing ran” step which subtracts a tick; the prose and test at k=23 say `combo_left = 0.4`. Make the branch explicit: on ending a swing, start the buffered next swing immediately or leave `combo_left` at its full configured value and return. On later idle ticks decrement it once. Recompute every expected tick from the implemented function, including equality at the active-window edges. The proposed k=8, 31, 54 examples are plausible only under that explicit order.
- **The headless hit-stop gate needs the production presentation registration.** PLAN.md:419-430 proposes adding only `HitStopPlugin` to `character_visuals_app`, then testing an impact. The current test harness (`src/visuals/character_gate.rs:50-75`) adds only `CharacterVisualsPlugin`; it has no `JuiceConfig` or normal `JuicePlugin`. A meaningful gate must add the production hit-stop and animation systems with their required config before `finish/cleanup`, then create three real animators. It must observe a real `MeleeHit`, pause attacker and victim, leave a bystander running, and compare `Time<Virtual>` and fixed tick count against an independent expected clock. `FixedTimesteps(1)` can have a zero-tick first update (project gate lesson), so warm up and count `Time<Fixed>` rather than asserting one tick for every `app.update()` from construction.
- **The plan claims a direct second-shove test validates melee integration, but it validates only the Tnua wrapper.** PLAN.md:336-339 directly calls `knock_back`; retain that focused regression, then add an integration case in which two legitimate strikes land on a victim before the first knockback finishes. This proves the strike scheduling and wrapper are connected. The probe used `force_forward: None` whereas the proposed implementation uses `Some(-direction)`; remeasure three directional cases after integration instead of treating the probe's exact distances as guaranteed.
- **The proposed `MeleeHit` is an applied-impact message, so it must not be emitted after death or a blocked strike.** `hitscan.rs:235` already guards a same-tick kill before `Dead` is inserted. `apply_strikes` should do likewise and only publish `DamageDealt`/`MeleeHit` after `Health::take`. If multiple attacks hit in one fixed tick, define deterministic ordering or key the output by attack/entity so the result does not depend on query iteration.
- **Stagger suppression must include guns.** The original plan cancels a victim's melee swing and zeros locomotion, but `fire_weapons` currently queries all living armed characters and never reads `HitReaction` (`hitscan.rs:124-164`). An armed character hit during stagger could still fire from a latched click or held SMG trigger in the same/next fixed tick. Gate gun firing on active reaction, clear the one-shot request, and add a focused headless case if the acceptance interpretation is that stagger interrupts all attacks.
- **The animation plan needs an explicit asset lookup and recovery policy.** `src/visuals/character.rs:49-86` stores graph node indices, not loaded `AnimationClip` durations. `AnimationClip::duration()` exists in pinned Bevy 0.19.1, but the system needs `Res<Assets<AnimationClip>>` plus clip handles; until an asset is loaded, use a bounded fallback rate and update it when available. A one-shot `die` clip for knockdown must not be left in the graph after `HitReaction` becomes `Steady`; explicitly transition to locomotion. The visual gate should assert those node transitions, not merely that a clip was requested once.
- **Bat rendering has another component to update.** `src/visuals/weapons.rs:142-165` currently changes only `MeshMaterial3d` and `Visibility`; adding a bat mesh requires `&mut Mesh3d` in that query. Preserve `HeldGun.barrel` as gun-only presentation metadata, and ensure muzzle-flash/tracer systems still react only to `ShotFired`. The existing primitive is attached under a scaled glTF joint (`weapons.rs:95-139`), so the new bat dimensions must use the same inverse model-scale treatment.
- **The plan's Open questions are stale.** `TASK_FINAL.md` has already resolved Q1 (2 m/s jabs), Q2 (key 1 toggles fists/bat), and Q3 (rotational camera shake). These are fixed decisions for this task. Do not re-open them.
- **Research/API verification.** The pinned source confirms `TnuaBuiltinKnockbackMemory::Shove` and the macro's `update_in_action_state` only replacing `state.input` (`bevy-tnua-0.32.0/src/builtins/knockback.rs:113-143,171-180`; `bevy-tnua-macros-0.3.0/src/scheme_derive/codegen.rs:88-105`). The documented [Tnua 0.32 controller API](https://docs.rs/bevy-tnua/0.32.0/bevy_tnua/controller/struct.TnuaController.html) exposes `action_interrupt`; [Avian 0.7 spatial queries](https://docs.rs/avian3d/0.7.0/avian3d/spatial_query/struct.SpatialQuery.html) support `cast_shape` with a filter; [Bevy 0.19 animation](https://docs.rs/bevy/0.19.1/bevy/animation/struct.AnimationPlayer.html) supports `pause_all`/`resume_all`; [Bevy 0.19 time](https://docs.rs/bevy/0.19.1/bevy/time/enum.TimeUpdateStrategy.html) documents `FixedTimesteps`. These support the chosen libraries. The plan's Capcom/SmashWiki references are design analogies; the GDD and pinned APIs are the implementation authority.

## 2. Updated understanding

`compose_sim` in `crates/gta_sim/src/lib.rs:26-86` loads validated simulation RON resources before adding the production plugins. `Character` uses a Tnua walk basis and jump action (`character/mod.rs:22-31`), with control feeding in `FixedUpdate` and Avian stepping in `FixedPostUpdate`. `CombatPlugin` (`combat/mod.rs:27-65`) runs `tick_loadouts` then gun firing in `HealthSystems::Damage`, pickup collection in `Pickup`, and dummy death/revival in `Death`, all under `PlayingSystems`. LMB is a latched input intent; unarmed clicks are currently consumed by gun firing without effect. `Loadout` holds an optional gun and three gun slots; a bat does not fit the `Weapon` enum's gun-indexed invariants. The range has three full `Character` dummies and six gun pickups in the city; the test area has no range.

`src/visuals/character.rs` owns one shared animation graph and per-model `CharacterAnimator`, while `src/visuals/weapons.rs` owns gun primitives. `src/juice/mod.rs` currently owns recoil and floating damage numbers. `src/camera/mod.rs:89-150` writes the aim ray before final visual recoil rotation. `src/visuals/character_gate.rs` has a headless client presentation harness with stand-in asset registrations. Runtime BRP helpers and the six-gun-pickup assertion live in `tools/qa/scenarios/t6.py`. GDD §4.2 and §8 require data-driven melee windows, local animation freeze on real time, and trauma; TASK_FINAL's resolved answers authorize the three deviations/choices above.

## 3. Revised approach

Keep combat rules in `gta_sim::combat`, with a `MeleeConfig` loaded from `assets/combat/melee.ron`, `Melee` and `HitReaction` components on each `Character`, and a buffered private `Strike` message between attack detection and damage application. In `FixedUpdate`, select equipment, advance attack/reaction state, cast a 0.35 m sphere on the explicit `[World, Character]` mask, apply health/reaction/knockback, then allow gun firing. The first world hit blocks the swing; an alive character hit produces `DamageDealt` and public `MeleeHit`. Keep the existing `DamageDealt` contract and allocate a shared monotonically wrapping attack serial for both guns and melee.

Use Tnua's built-in knockback action. Reset its memory to `Shove` when interrupting an already active knockback; otherwise a second shove only replaces input. Keep the victim facing the attacker with `force_forward`, but measure displacement under that actual configuration. Use `Time<Fixed>` for attack windows, stagger and knockdown; use `Time<Real>` only for visual hit-stop and camera shake. `MeleeHit` is a buffered `Message` because client consumers run later in the frame; Bevy `On<Add, ...>` observers are for one-time component attachment. Camera shake is applied after writing `AimIntent`, as authorized. All tunable values belong to `melee.ron`, `juice.ron`, `visual.ron`, or `render.ron` as appropriate; code `const`s are limited to paths and laws.

## 5. Risk areas

- **Reach and physics:** 2 m/s jabs are an approved tuning exception. The earlier flat-ground probe found about 0.177 m slide per jab, but the integrated `force_forward`, moving actors, walls, and repeated strikes may alter it. The finisher-reach gate must use the production headless app.
- **Clock and ordering:** hit-stop must not alter `Time<Virtual>` or `FixedUpdate`; only animations pause. Buffered `Strike` and `MeleeHit` lifetimes and `OnExit(Wasted)` cleanup need explicit ordering so old messages do not fire after respawn.
- **Head sensors:** the head sensor remains physically attached to an upright capsule during knockdown. Filter it from hitscan while down; keep the body collider queryable. Verify a shot at a geometric point that intersects both standing head sensor and downed body.
- **Animation asset timing:** loaded clip duration may be unavailable on the first action frame. A fallback rate must be bounded and corrected when the clip arrives. The Kenney `die` clip is a visual stand-in for knockdown, so recovery quality is an owner-run concern.
- **Client scope:** `HeldGun` also carries gun muzzle metadata. Showing a bat through it must not produce gun VFX or corrupt muzzle assumptions. Primitive dimensions inherit the glTF joint's transform unless compensated.
- **QA stability:** BRP may observe state between fixed ticks and screenshot capture has latency. Poll state with deadlines and space images; use headless tests for sharp window/clock assertions.
